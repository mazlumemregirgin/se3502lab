Object-Oriented Go

Go'da OOP'yi anla — Java zihinsel modelinle karşılaştırmalı bir rehber

01 / Structs
Java'daki Class = Go'daki Struct

Go'da struct, Java'daki class'ın veri taşıyan yarısıdır. Behavior (davranış) ayrı olarak method'larla eklenir.

Java — Class 
public class User {
    private int id;
    private String username;
    private String email;
    private boolean isActive;

    // Constructor
    public User(int id, String username) {
        this.id = id;
        this.username = username;
        this.isActive = true;
    }
}
Go — Struct 
type User struct {
    ID       int
    Username string
    Email    string
    IsActive bool
}

// Constructor yok — factory function kullanılır
func NewUser(id int, username string) User {
    return User{
        ID: id, Username: username, IsActive: true,
    }
}
💡
Constructor yok! Go'da özel bir constructor sözdizimi yoktur. Bunun yerine convention olarak NewXxx() adlı factory function'lar kullanılır. Java'daki new User() çağrısının karşılığıdır.

Initialization Stilleri

Java
// new keyword zorunlu
User u1 = new User(1, "alice");

// null (Java'da default referans)
User u2 = null;
Go
// Named fields ile literal
u1 := User{ID: 1, Username: "alice"}

// Zero value — tüm alanlar sıfırlanır
// 0, "", false, nil
var u2 User

// Pointer ile
u3 := &User{ID: 2, Username: "bob"}

🧠 Zihinsel Model

Java'da bir object yaratmak için her zaman new kullanmak zorundasın ve bellek heap'te allocate edilir. Go'da ise bir struct değeri (value) stack'te de yaşayabilir. &User{} dersen pointer alırsın ve heap'e gider — ama bu kararı genellikle compiler optimize eder (escape analysis). Stack vs Heap ayrımı Go'da sana daha şeffaftır.

🔒 Erişim Kontrolü

Java: private/public/protected. Go: büyük harf = exported (public), küçük harf = unexported (package-private). private keyword'ü yok.

⚡ Zero Value

Go'da tüm tipler için anlamlı bir zero value vardır. int → 0, string → "", bool → false. NullPointerException korkusu yok!

📦 Paket Sistemi

Java'daki class-level encapsulation yerine Go package-level encapsulation kullanır. Aynı paketteki tüm dosyalar unexported alanları görebilir.

02 / Composition
Inheritance Yok, Composition Var

Java'da extends ile kalıtım kurarsın. Go bunu kasıtlı olarak reddeder. Bunun yerine struct embedding kullanılır.

🚫
Go'da extends yoktur. class BlogPost extends Author gibi bir şey yazamazsın. Go ekibi bunu bilinçli bir tasarım kararı olarak almıştır. "is-a" ilişkisi yerine "has-a" ilişkisini tercih ederler.
Java — Inheritance (is-a)
public class Author {
    public String fullName;
    public String bio;
}

// BlogPost IS-A Author (kalıtım)
public class BlogPost extends Author {
    public String title;
    public String content;
}

// Kullanım
BlogPost post = new BlogPost();
post.fullName = "Grace Hopper"; // inherited
Go — Embedding (has-a, promoted)
type Author struct {
    FullName string
    Bio      string
}

// BlogPost HAS-AN Author (gömülü)
type BlogPost struct {
    Author   // anonymous embed — promotion!
    Title   string
    Content string
}

// Kullanım — promoted field'a direkt eriş
post.FullName = "Grace Hopper"
// ya da explicit:
post.Author.FullName = "Grace Hopper"
✨
Field Promotion! Anonymous (isimsiz) bir struct embed ettiğinde, iç struct'ın field ve method'ları dış struct'a "promote" olur. Yani post.FullName yazabilirsin, post.Author.FullName yazmak zorunda değilsin. Java'daki super.field mantığına benzer ama daha doğal görünür.

Çoklu Composition — Java'da Mümkün Değil!

Go — Birden fazla struct embed etmek
type Timestamps struct {
    CreatedAt time.Time
    UpdatedAt time.Time
}

type Auditable struct {
    CreatedBy string
    UpdatedBy string
}

// İKİ struct'ı aynı anda embed edebilirsin
// Java'da multiple inheritance YASAK — Go'da sorun yok!
type Article struct {
    Timestamps  // promoted: article.CreatedAt
    Auditable   // promoted: article.CreatedBy
    Title string
    Body  string
}
⚠️
Diamond Problem yok! Java multiple inheritance'ı yasaklar çünkü diamond problem'e yol açar. Go embedding'de eğer iki embed'de aynı isimde field/method varsa, compiler seni uyarır ve explicit erişim zorunlu olur. Otomatik çözüm yok — sen karar verirsin.
Özellik Java Go
Kalıtım extends ile tek sınıftan Yok — struct embedding kullan
Multiple Inheritance Yasak (interface hariç) Çoklu embedding ile mümkün
super keyword Var, parent'a erişim sağlar Yok — struct.EmbeddedType.Field
Override @Override annotation Aynı isimde method tanımla (shadowing)
İlişki tipi is-a (BlogPost IS-A Author) has-a (BlogPost HAS-AN Author)
03 / Methods & Receivers
Pointer vs Value Receiver

Go'da method'lar struct'ın içinde değil, dışında tanımlanır. Ve receiver tipi seçimi kritik öneme sahiptir.

Java — Instance Method
public class BankAccount {
    private double balance;

    // Method class içinde tanımlanır
    // 'this' implicit olarak pass edilir
    public void deposit(double amount) {
        this.balance += amount; // state değişir
    }

    public double getBalance() {
        return this.balance; // okuma
    }
}
Go — Method with Receiver
type BankAccount struct {
    balance float64
}

// POINTER receiver — state değiştiriyor!
// *BankAccount = Java'daki 'this' gibi
func (a *BankAccount) Deposit(amount float64) {
    a.balance += amount
}

// VALUE receiver — sadece okuma
func (a BankAccount) GetBalance() float64 {
    return a.balance
}

🧠 Receiver = Java'daki "this"

Java'da this her zaman nesnenin referansıdır (pointer). Go'da ise seçim yapman gerekir: *T (pointer receiver) ile Java'daki gibi orijinal nesneyi değiştirebilirsin. T (value receiver) ile ise metodun bir kopyası üzerinde çalışırsın — orijinal değişmez. Java'da bu ayrım yoktur çünkü objeler zaten referans tipindedir.

Ne Zaman Hangisini Kullanmalı?

🖊️ Pointer Receiver *T

State değiştiriyorsan — a.balance += amount gibi. Struct büyükse (kopyalama pahalı). Tutarlılık için: struct'ın diğer method'ları pointer receiver kullanıyorsa sen de kullan.

📖 Value Receiver T

Sadece okuma yapıyorsan. Küçük, immutable struct'larda — time.Time gibi. Fonksiyonel, side-effect'siz davranış istiyorsan.

Kritik Tuzak — Value Receiver ile State Değiştirme
type Counter struct { count int }

// ❌ YANLIŞ: Value receiver — kopya üzerinde çalışır!
func (c Counter) WrongIncrement() {
    c.count++ // SADECE KOPYA değişir, orijinal değişmez!
}

// ✅ DOĞRU: Pointer receiver
func (c *Counter) Increment() {
    c.count++ // Orijinal struct değişir
}

func main() {
    c := Counter{}
    c.WrongIncrement()
    fmt.Println(c.count) // → 0  (değişmedi!)
    c.Increment()
    fmt.Println(c.count) // → 1  ✓
}
☕
Java Developer Tuzağı: Java'da tüm nesneler referans tipidir. account.deposit(100) her zaman orijinal nesneyi değiştirir. Go'da bunu varsayamazsın! Value receiver kullandıysan değişiklik kaybolur. Bu Go'da en sık yapılan hatalardan biridir.
04 / Interfaces
Implicit Interface — Go'nun En Güçlü Özelliği

Java'da interface'i implement etmek için implements yazman gerekir. Go'da ise hiçbir şey yazmazsın — method imzaları uyuşuyorsa otomatik olarak implement edilmiş sayılır.

Java — Explicit Implementation
public interface Animal {
    String Sound();
    String Name();
}

// 'implements' ZORUNLU — aksi halde hata
public class Dog implements Animal {
    public String Sound() { return "Woof"; }
    public String Name()  { return "Dog"; }
}

// Dog Animal interface'ini implement ediyor
Animal a = new Dog();
Go — Implicit (Duck Typing)
type Animal interface {
    Sound() string
    Name()  string
}

// 'implements Animal' yazmıyoruz!
type Dog struct{}

func (d Dog) Sound() string { return "Woof" }
func (d Dog) Name()  string { return "Dog"  }

// Dog otomatik olarak Animal'dır!
var a Animal = Dog{} // ✓ çalışır

🦆 Duck Typing — "Ördek gibi yürüyorsa, ördek gibi vaklıyorsa..."

Go'nun interface'i "duck typing" prensibine dayanır. Bir tip, bir interface'in tüm method'larını implement ediyorsa, o interface'i satisfy eder — bunu hiçbir yerde belirtmene gerek yoktur. Bu, Java'nın nominal typing'ine karşın structural typing'dir. Avantajı: bir kütüphaneyi değiştirmeden onun tiplerine kendi interface'ini uygulayabilirsin!

Polymorphism Örneği

Go — Interface ile Polymorphism
type Shape interface {
    Area()      float64
    Perimeter() float64
}

type Rectangle struct { Width, Height float64 }
type Circle    struct { Radius float64 }

func (r Rectangle) Area()      float64 { return r.Width * r.Height }
func (r Rectangle) Perimeter() float64 { return 2 * (r.Width + r.Height) }
func (c Circle)    Area()      float64 { return math.Pi * c.Radius * c.Radius }
func (c Circle)    Perimeter() float64 { return 2 * math.Pi * c.Radius }

// Java'daki List<Shape> shapes gibi!
func PrintShapeInfo(shapes []Shape) {
    for _, s := range shapes {
        fmt.Printf("Area: %.2f, Perimeter: %.2f\n",
            s.Area(), s.Perimeter())
    }
}

func main() {
    shapes := []Shape{
        Rectangle{Width: 5, Height: 3},
        Circle{Radius: 4},
    }
    PrintShapeInfo(shapes) // polymorphic dispatch!
}
Özellik Java Go
Implementation Bildirimi implements Foo zorunlu Yok — implicit (structural typing)
Retroactive Implementation İmkansız (class'ı değiştirmen gerek) Mümkün! Başka paketteki tiplere uygulanabilir
Interface Field Constant field'lar olabilir Sadece method imzaları — field yok
Default Method Java 8+ default keyword Yok — composition ile çözülür
Abstract Class Karşılığı abstract class Yok — interface + embedding ile yaklaşılır
05 / Dependency Injection
DI — Framework Yok, Interface Yeter

Java'da Spring @Autowired ile DI yaparsın. Go'da framework'e ihtiyaç yoktur — interface'ler constructor'a inject edilir.

Java — Spring DI
public interface NotificationService {
    void send(String msg);
}

// Spring bean
@Service
public class EmailService
        implements NotificationService {
    public void send(String msg) { ... }
}

@Service
public class OrderService {
    @Autowired  // framework inject eder
    private NotificationService notifier;
}
Go — Manuel DI (interface ile)
type Notifier interface {
    Send(msg string) error
}

type EmailService struct{}
func (e EmailService) Send(msg string) error {
    // email gönder...
    return nil
}

type OrderService struct {
    notifier Notifier // interface field!
}

// Constructor injection — Spring yok!
func NewOrderService(n Notifier) *OrderService {
    return &OrderService{notifier: n}
}

Test Edilebilirlik — Mock Kolayca Yazılır

Go — Interface ile Mock (Mockito'ya gerek yok!)
// Test dosyasında mock tanımı
type MockNotifier struct {
    SentMessages []string
}

func (m *MockNotifier) Send(msg string) error {
    m.SentMessages = append(m.SentMessages, msg)
    return nil
}

// Test — gerçek email servisi gerekmez!
func TestOrderService_PlaceOrder(t *testing.T) {
    mock := &MockNotifier{}
    svc := NewOrderService(mock) // inject!

    svc.PlaceOrder("Order #42")

    // Mock'a mesaj geldi mi?
    if len(mock.SentMessages) != 1 {
        t.Fatal("Expected 1 notification")
    }
}
🎯
Mockito'ya ihtiyaç yok! Java'da mock için genellikle Mockito framework'ü kullanırsın. Go'da interface'ler implicit olduğu için, test dosyana sadece birkaç satır struct + method yazarak mock oluşturursun. Dış bağımlılık sıfır, test okunabilirliği maksimum.
📐
Interface Boyutu Felsefesi: Go kültüründe interface'ler küçük tutulur. Java'da Repository interface'inde 15 method görmek normalken, Go'da genellikle 1-3 method olur. Go standart kütüphanesinin en önemli interface'i io.Reader'dır — sadece 1 method içerir: Read(p []byte) (n int, err error). Az, daha iyi.
